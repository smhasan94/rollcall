# Contributing to rollcall

Issues and pull requests are welcome. The house rules are in force for every change: the same
input gives byte-identical output, parsers return errors instead of panicking, golden files
are only rewritten by `scripts/regen-golden.sh`, files under `fixtures/` only by
`scripts/regen-fixtures.sh`, and `cargo fmt --all --check`,
`cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass.

The most common contribution is a module for the identifier database, so that comes first.

## Adding a module to the identifier database

The identifier database (`crates/rollcall-identifiers/db/identifiers.yaml`) tells rollcall,
for each Zephyr module, which upstream project the fork is, its purl and CPE, and the upstream
version of each fork commit Zephyr pins. Its conventions are in
[docs/identifiers.md](docs/identifiers.md); read the *PURL convention* and *CPE convention*
sections once. The steps below take about ten minutes, most of it waiting for step 6.

You need `git`, `curl`, `jq`, `python3`, a Rust toolchain, and the network (steps 3 and 6).

Throughout, `<module>` is the west module name, exactly as in Zephyr's `west.yml` (for
example `trusted-firmware-a`).

### 1. Check that the module is missing and pinned

```sh
grep -n "^  <module>:" crates/rollcall-identifiers/db/identifiers.yaml   # no output: missing
grep "^<module> " crates/rollcall-core/tests/data/zephyr-manifest-pins.txt
```

The second command lists each commit Zephyr v4.2.0 to v4.4.2 pins for the module, with its
fork URL and the releases that pin it. No output means those releases do not pin the module:
it cannot get a generated version table, so give it a `git_tag` rule instead (see
`cjson` in the database) and skip steps 4 and 6.

### 2. Find the upstream

From the fork's readme (`README.md`, `README.rst` or `readme.rst`, at the pinned commit:
`https://raw.githubusercontent.com/zephyrproject-rtos/<module>/<commit>/<file>`) find the
upstream project the fork follows:

- its **name** (as the project spells it), **homepage**, and **supplier** (the organisation
  that releases it; if the database already has a module from the same organisation, spell
  the supplier the same way);
- its **repository URL**, which goes in the purl's `vcs_url`;
- how its **releases are tagged** in that repository
  (`git ls-remote --tags <repository URL>` lists them: `v2.12.0`, `TF-Mv2.2.0`, …) or, if the
  fork does not share the upstream history, which **file** in the fork names the version.

The purl is always
`pkg:generic/<name>@{version}?vcs_url=git+<repository URL>`, with `<name>` in lower case.

### 3. Look the CPE up in the NVD dictionary

A module gets a `cpe` only when NVD's CPE dictionary lists its vendor:product. Guess the
likely pairs (search <https://nvd.nist.gov/products/cpe/search> for the project's name, or
read the CPE of one of its CVEs) and check each, with both part `a` (application) and part
`o` (operating system or firmware), since the dictionary may file it under either:

```sh
scripts/nvd-spot-check.sh 'cpe:2.3:a:<vendor>:<product>' 'cpe:2.3:o:<vendor>:<product>'
```

- A non-deprecated match: that is the `cpe`, as
  `'cpe:2.3:<part>:<vendor>:<product>:{version}:*:*:*:*:*:*:*'`, with the part that matched.
- Any other pair that matched (even only deprecated entries) may still carry CVEs. Count them
  with the NVD CVE API; each pair with CVEs goes in `cpe_aliases`:

  ```sh
  curl -s 'https://services.nvd.nist.gov/rest/json/cves/2.0?virtualMatchString=cpe:2.3:<part>:<vendor>:<product>' | jq .totalResults
  ```
- That the dictionary has no entry for the exact versions you will derive is normal (NVD's
  CVE configurations use version ranges, which scanners match); the vendor:product is what
  must be listed.
- No match: write no `cpe`. Put a `# No cpe: <why>. Checked <today's date>.` comment (date
  as `YYYY-MM-DD`) where the `cpe:` line would go.

### 4. Add the entry

Add the entry to `crates/rollcall-identifiers/db/identifiers.yaml` under `modules:`, **in
name order** (byte order: `-` sorts before `_`, and both before letters). Copy the shape of the
example at the end of this section. Leave the table's generated block empty; step 6 fills it:

```yaml
    version_rule:
      kind: manual
      table:
        # BEGIN generated by scripts/regen-version-tables.sh; do not edit
        # END generated
```

### 5. Tell the version-table script how to find the version

Add the module to `DERIVE` in `scripts/version-tables.py`, next to a module derived the
same way:

- `"how": "tag"`, `"upstream"` (the repository) and `"tag"` (a regex with group `v`) when the
  fork shares the upstream's history: the version is the newest upstream release tag that is
  an ancestor of the pinned commit. Most forks are like this.
- `"how": "file"`, `"paths"`, `"regex"` and `"fmt"` when a file in the fork states the
  version (see `mbedtls`).
- `"how": "log"` when the fork imports releases as snapshots and names them in commit
  subjects (see `libmetal`).

### 6. Generate the version table

```sh
scripts/regen-version-tables.sh
```

It fetches Zephyr's manifests, derives a version for every pinned commit of every module, and
writes the rows between the markers. The first run clones several repositories (blobless,
cached in `.cache/version-tables/`) and takes a few minutes. It fails, naming the commit, if
any pinned commit is left without a version. Check the new rows: each comment names the
releases pinning the commit and how the version was found. Nothing else in the database
should change; if other modules' rows changed, an upstream released since the last run, so
leave those rows out of your change (`git checkout -p`) unless you mean to update them.

The script ends by running the identifier tests. The seed tests
(`identify::seed::tests::seed_*`) fail until step 7 is done, which stops the script before it
prints its summary, so look at the result yourself:

```sh
git diff crates/rollcall-identifiers/db crates/rollcall-core/tests/data/zephyr-manifest-pins.txt
```

### 7. Register the module with the tests and the docs

- `crates/rollcall-core/src/identify/seed.rs`: add the module to `SCOPED` (in name order) and,
  if it has a `cpe`, to `NVD_LISTED` (with its `cpe:2.3:<part>:<vendor>:<product>:` prefix),
  and each alias to `NVD_ALIASES`. Fix the array lengths.
- `docs/identifiers.md`: add a row to the *Module table* (in name order):
  ``| `<module>` | [<name>](<homepage>) | <versions from the table> | <how they are derived> | <`a:vendor:product` or `none: <why>`> |``,
  and the module to the *How a version is derived* list for its method.

### 8. Bump the database version

A new module is a MINOR release of the database. Change the version in both places, to the
same value (for example `1.0.0` to `1.1.0`), and refresh the lock file:

```sh
#   crates/rollcall-identifiers/db/identifiers.yaml:  db_version: '1.1.0'
#   crates/rollcall-identifiers/Cargo.toml:           version = "1.1.0"
cargo update -p rollcall-identifiers --offline
```

(A fix to an existing entry is a PATCH release instead.)

### 9. Lint and test

```sh
scripts/lint-identifiers.sh
cargo test -p rollcall-core --lib identify::
cargo test -p rollcall-core --test docs --test identify --test identify_lint
scripts/regen-golden.sh
```

SBOMs record the `db_version` that resolved them (`rollcall:identifiers:db-version`), so the
version bump changes the goldens rendered with the database (`old-mbedtls`):
`scripts/regen-golden.sh` rewrites them; check that the diff is only that property.

`scripts/lint-identifiers.sh` is what CI's `identifiers-lint` job runs. It must end with
`0 finding(s)`; each finding is `file:line: rule: message`. It checks the schema, purl and CPE
syntax, duplicate and unsorted modules, that `db_version` equals the crate version, that every
table row resolves to a purl (and CPE), and that every module of the `fixtures/zephyr` builds
still resolves.

### 10. Open the pull request

Title it `identifiers: add <module>`, and paste the `nvd-spot-check.sh` output from step 3
into the description.

### Example: `trusted-firmware-a`

This is a complete entry, as added by following the steps above. A test
(`contributing_walkthrough_adds_trusted_firmware_a_and_resolves` in
`crates/rollcall-cli/tests/identifiers.rs`) inserts it into a copy of the database, lints the
copy and resolves each of its rows, so the example stays correct.

<!-- example:start -->
```yaml
  trusted-firmware-a:
    upstream:
      name: Trusted Firmware-A
      homepage: https://git.trustedfirmware.org/TF-A/trusted-firmware-a.git
      supplier: TrustedFirmware.org
    purl: 'pkg:generic/trusted-firmware-a@{version}?vcs_url=git+https://git.trustedfirmware.org/TF-A/trusted-firmware-a.git'
    cpe: 'cpe:2.3:o:trustedfirmware:trusted_firmware-a:{version}:*:*:*:*:*:*:*'
    version_rule:
      kind: manual
      table:
        # BEGIN generated by scripts/regen-version-tables.sh; do not edit
        '0a29cac8fe0f7bdb835b469d9ea11b8e17377a92': '2.13.0'  # v4.3.0 v4.3.1; newest ancestor tag v2.13.0
        '4aef38a5bf03edfa615c1f8af5a49e7065f9fb3f': '2.14.0'  # v4.4.0 v4.4.1 v4.4.2; newest ancestor tag v2.14.0
        '713ffbf96c5bcbdeab757423f10f73eb304eff07': '2.10.0'  # v4.2.0 v4.2.1 v4.2.2; newest ancestor tag v2.10.0
        # END generated
```
<!-- example:end -->

Its step 3, run on 2026-10-01: `scripts/nvd-spot-check.sh` found
`o:trustedfirmware:trusted_firmware-a` (104 entries, none deprecated) and
`a:arm:trusted_firmware-a` (47 entries, all deprecated); the CVE API counts 7 CVEs under the
first and none under the second, so the entry has that `cpe` and no `cpe_aliases`. The
dictionary has no entry yet for 2.10.0, 2.13.0 or 2.14.0. Step 5 used `"how": "tag"` with
upstream `https://git.trustedfirmware.org/TF-A/trusted-firmware-a.git` and tag
`^v(?P<v>\d+\.\d+\.\d+)$`.

## Other changes

- **Golden files** (`crates/rollcall-core/tests/golden/`): run `scripts/regen-golden.sh` and
  review the diff like code.
- **Fixtures** (`fixtures/`): real Zephyr builds, regenerated by `scripts/regen-fixtures.sh`
  (see [docs/fixtures.md](docs/fixtures.md)); never edit them by hand. The ESP-IDF builds
  (`fixtures/esp-idf/`) come from `scripts/regen-fixtures-esp-idf.sh`, which needs Docker.
- **ESP-IDF table** (`crates/rollcall-core/db/esp-idf.yaml`): the subsystems split out of
  `esp-idf`, their archives and upstream versions, and the blob directories, checked against
  the pinned ESP-IDF release; see [docs/esp-idf.md](docs/esp-idf.md).
- **Subsystem table** (`crates/rollcall-core/db/subsystems.yaml`): checked by
  `scripts/verify-subsystems.sh`; see [docs/subsystems.md](docs/subsystems.md).
